# **WebSockets in Django using Django Channels**

Since you're working with a **React frontend and Django REST Framework backend** for your E-library project, I'll explain how to implement WebSockets in that architecture.

The most common Django solution is **Django Channels**.

With Django Channels, you can build:

- Real-time chat applications.
- Notifications.
- Online/offline user status.
- Live messaging.
- Typing indicators.
- Real-time updates without refreshing the page.

Let's start with the fundamentals.

## **1. What is a WebSocket?**

Normally, when React communicates with Django using HTTP, the communication works like this:

**HTTP communication**

**React**

I need new messages

HTTP request

**Django**

Here are your messages

HTTP response

The request-response cycle ends. React must make another request to get new data.

With WebSockets, React establishes a persistent connection with Django.

**WebSocket communication**

**React frontend**

Persistent connection

Both sides can send messages at any time

**Django backend**

The connection remains open until one side closes it or it is interrupted.

For example, when user A sends a message, Django can immediately send that message to user B without user B requesting it.

That's the main benefit of WebSockets.

## **2. What is Django Channels?**

Django's traditional request handling is based on HTTP. Django Channels extends Django to support long-lived connections and protocols such as WebSockets.

It uses ASGI (Asynchronous Server Gateway Interface) to handle these connections.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub+1



There are four important concepts you should understand:

| Concept       | Responsibility                                |
| ------------- | --------------------------------------------- |
| Consumer      | Handles WebSocket connections and messages    |
| Routing       | Directs WebSocket connections to consumers    |
| Channel Layer | Enables communication between consumers       |
| Redis         | Stores and distributes channel-layer messages |

We'll understand each one while building a small chat application.

## **6. Create a WebSocket Consumer**

This is the most important part.

In Django Channels, a **Consumer** is similar to a Django view, but instead of handling one HTTP request and returning one response, it handles a connection that can remain open.

Create `api/consumers.py`:

```
import jsonfrom channels.generic.websocket import AsyncWebsocketConsumerclass ChatConsumer(AsyncWebsocketConsumer):    async def connect(self):        # Get room name from the URL        self.room_name = self.scope["url_route"]["kwargs"]["room_name"]        # Create a group name        self.room_group_name = f"chat_{self.room_name}"        # Add this connection to the group        await self.channel_layer.group_add(            self.room_group_name,            self.channel_name        )        # Accept the WebSocket connection        await self.accept()        print("WebSocket connected!")    async def disconnect(self, close_code):        # Remove this connection from the group        await self.channel_layer.group_discard(            self.room_group_name,            self.channel_name        )        print("WebSocket disconnected!")    async def receive(self, text_data):        # Receive a message from React        data = json.loads(text_data)        message = data["message"]        # Send message to everyone in the room        await self.channel_layer.group_send(            self.room_group_name,            {                "type": "chat_message",                "message": message,            }        )    async def chat_message(self, event):        # Send the message to the connected client        await self.send(text_data=json.dumps({            "message": event["message"]        }))
```

Let's understand these four methods.

### `connect()`

```
async def connect(self):
```

Called when React establishes a new WebSocket connection.

For example, when a user opens a chat room, Django executes this method.

### `disconnect()`

```
async def disconnect(self, close_code):
```

Called when the WebSocket connection closes.

For example, when the user closes the browser or navigates away.

### `receive()`

```
async def receive(self, text_data):
```

Called whenever React sends a message through the WebSocket.

For example:

```
{
    "message": "Hello!"
}
```

Django receives this message and processes it.

### `chat_message()`

```
async def chat_message(self, event):
```

This method receives messages distributed through the channel layer and sends them to the connected React clients.

One important detail:

```
"type": "chat_message"
```

Tells Channels which consumer method to execute.

The event type determines the handler method. For example, `chat.message` would call `chat_message`.&#x20;

## **8. Configure ASGI**

This is another important step.

Django traditionally uses `wsgi.py` for WSGI servers. For WebSockets, we need an ASGI application.

Open `config/asgi.py` and replace its contents with:

```
import osfrom django.core.asgi import get_asgi_applicationos.environ.setdefault(    "DJANGO_SETTINGS_MODULE",    "config.settings")# Initialize Django firstdjango_asgi_app = get_asgi_application()from channels.routing import (    ProtocolTypeRouter,    URLRouter,)from channels.auth import AuthMiddlewareStackfrom channels.security.websocket import OriginValidatorfrom api.routing import websocket_urlpatternsapplication = ProtocolTypeRouter({    # Normal HTTP requests    "http": django_asgi_app,    # WebSocket connections    "websocket": OriginValidator(        AuthMiddlewareStack(            URLRouter(websocket_urlpatterns)        ),        [            "http://localhost:5173",        ]
```

Replace the allowed origin with your actual React frontend origin.

What does `ProtocolTypeRouter` do?

It distinguishes between different connection types:

- `http`: Sends normal HTTP requests to Django.
- `websocket`: Sends WebSocket connections to Django Channels.

`URLRouter` finds the appropriate consumer based on the WebSocket URL.

`AuthMiddlewareStack` provides Django session-based authentication information to consumers.

`OriginValidator` restricts which browser origins can establish WebSocket connections.&#x20;

## **9. Connect React to Django**

Now let's connect your React application to the Django WebSocket server.

Unlike HTTP, you don't use `fetch()` or Axios to send WebSocket messages. You use the browser's native `WebSocket` API.

Create a React component:

```
import { useEffect, useRef, useState } from "react";

function Chat() {

    const socketRef = useRef(null);

    const [messages, setMessages] = useState([]);
    const [message, setMessage] = useState("");

    useEffect(() => {

        // Establish WebSocket connection
        const socket = new WebSocket(
            "ws://localhost:8000/ws/chat/general/"
        );

        socketRef.current = socket;

        // Connection established
        socket.onopen = () => {
            console.log("Connected to Django!");
        };

        // Receive messages from Django
        socket.onmessage = (event) => {

            const data = JSON.parse(event.data);

            setMessages((previous) => [
                ...previous,
                data.message
            ]);
        };

        // Handle connection errors
        socket.onerror = (error) => {
            console.error("WebSocket error:", error);
        };

        // Connection closed
        socket.onclose = () => {
            console.log("Disconnected!");
        };

        // Clean up connection
        return () => {
            socket.close();
            socketRef.current = null;
        };

    }, []);

    // Send message to Django
    const sendMessage = () => {

        if (
            socketRef.current?.readyState === WebSocket.OPEN
        ) {

            socketRef.current.send(
                JSON.stringify({
                    message: message
                })
            );

            setMessage("");
        }
    };

    return (
        <div>

            <h2>Chat Room</h2>

            {messages.map((msg, index) => (
                <p key={index}>{msg}</p>
            ))}

            <input
                value={message}
                onChange={(e) => setMessage(e.target.value)}
                placeholder="Enter message..."
            />

            <button onClick={sendMessage}>
                Send
            </button>

        </div>
    );
}

export default Chat;
```

Let's understand the important JavaScript methods:

| Method               | What it does                    |
| -------------------- | ------------------------------- |
| `new WebSocket(url)` | Creates a connection            |
| `onopen`             | Runs when the connection opens  |
| `onmessage`          | Runs when a message arrives     |
| `send()`             | Sends a message                 |
| `onclose`            | Runs when the connection closes |
| `onerror`            | Handles connection errors       |

# **11. What is Redis, and why do we need it?**

You might be wondering why we installed `channels_redis`.

Imagine your Django application has two server processes:

- Server A handles React user 1.
- Server B handles React user 2.

User 1 sends a message to Server A.

How does Server B know that it should deliver this message to user 2?

That's where Redis comes in.

**React user 1**

**Django Server A**

Receives message

**Redis Channel Layer**

Distributes events between servers

**Django Server B**

Receives the event

**React user 2**

Receives the message immediately

Redis acts as a communication layer between Django processes.

You don't necessarily need Redis while experimenting locally with one process, but you should use Redis for a production deployment with Channels. The official Channels project recommends `channels_redis` for production channel layers.&#x20;

# **13. Important: WebSockets and JWT authentication**

I want to highlight something important because your existing React + Django project uses JWT.

In our example, we used:

```
AuthMiddlewareStack(    URLRouter(websocket_urlpatterns))
```

This integrates Django's session-based authentication with WebSockets.

**However, it does not automatically authenticate your JWT access tokens.**

If your React application stores JWT tokens in `localStorage`, you need additional authentication middleware for WebSocket connections.

You also need to check that the authenticated user is allowed to join the requested chat room.

The browser's native WebSocket API does not let you attach arbitrary HTTP headers such as `Authorization` when creating a connection. Avoid putting access tokens in URL query parameters because URLs can be exposed in logs.

You can implement secure JWT authentication using custom Channels middleware or an appropriately configured secure cookie authentication approach.&#x20;

# **3. Authenticate WebSocket connections using JWT**

This is the most important part of the integration.

You already use Simple JWT for your REST API. However, Django Channels does not automatically use DRF's `JWTAuthentication`.

The standard `AuthMiddlewareStack` authenticates Django session users, not your JWT tokens.

We need custom middleware that:

1. Reads the Authorization header.
2. Extracts the JWT access token.
3. Validates the token using Simple JWT.
4. Retrieves the corresponding Django user.
5. Attaches that user to the WebSocket connection.

Channels officially supports custom authentication middleware for this purpose.&#x20;

# **4. Create your WebSocket Consumer**

Think of a consumer as a controller that manages a WebSocket connection.

For your chat app, let's create a consumer for individual conversations.

### **Step 2. Create a WebSocket service**

I recommend creating a separate service rather than writing WebSocket logic directly inside your chat screen.

Your Flutter structure could look like:

```
lib/
│
├── services/
│   ├── api_service.dart
│   └── chat_socket_service.dart
│
├── models/
│   └── message.dart
│
├── screens/
│   └── chat_screen.dart
│
└── main.dart
```

Create `services/chat_socket_service.dart`:

```

import 'dart:convert';

import 'package:flutter_secure_storage/flutter_secure_storage.dart';
import 'package:web_socket_channel/io.dart';

class ChatSocketService {

  static const storage = FlutterSecureStorage();

  IOWebSocketChannel? _channel;

  // Expose incoming messages to Flutter UI
  Stream<dynamic>? get messages => _channel?.stream;

  // Connect to a conversation
  Future<void> connect(int conversationId) async {

    final accessToken = await storage.read(
      key: 'access',
    );

    if (accessToken == null) {
      throw Exception('User is not authenticated');
    }

    final uri = Uri.parse(
      'ws://10.0.2.2:8000/ws/chat/$conversationId/',
    );

    _channel = IOWebSocketChannel.connect(
      uri,
      headers: {
        'Authorization': 'Bearer $accessToken',
      },
    );

    // Wait for connection establishment
    await _channel!.ready;
  }

  // Send a message
  void sendMessage(String message) {

    if (_channel == null) {
      throw Exception('WebSocket is not connected');
    }

    _channel!.sink.add(
      jsonEncode({
        'message': message,
      }),
    );
  }

  // Disconnect
  Future<void> disconnect() async {

    await _channel?.sink.close();

    _channel = null;
  }
}

```

**Important: Why&#x20;**`10.0.2.2`**?**

If you're using the Android emulator, `localhost` refers to the emulator itself, not your computer.

Use:

| Environment             | Backend address                  |
| ----------------------- | -------------------------------- |
| Android emulator        | `10.0.2.2:8000`                  |
| iOS simulator           | Usually `127.0.0.1:8000`         |
| Physical Android device | Your computer's local network IP |
| Production              | Your Railway domain              |

The key authentication code is:

```
headers: {
    'Authorization': 'Bearer $accessToken',
},
```

This sends your JWT access token during the WebSocket handshake.

`IOWebSocketChannel` supports custom connection headers on Flutter's native platforms.&#x20;

# **8. How does message delivery actually work?**

Suppose User A and User B are both connected to conversation 15.

User A sends this JSON from Flutter:

```
{
    "message": "Hello User B!"
}
```

Django receives it in:

```
async def receive_json(self, content, **kwargs):
```

Then Django executes:

```
await self.channel_layer.group_send(    self.room_group_name,    {        "type": "chat.message",        "message": content["message"],        "sender_id": self.user.id,    })
```

Because both users have joined the same group, Channels distributes the message to both connections.

**Conversation 15**

Live

**User A**

Hello User B!

Sent through WebSocket

Django Channels broadcasts the message

**User B**

Hello User B!

Received instantly

Notice that you don't have to make another HTTP request to retrieve this new message.

# **9. How does this work with your DRF database?**

One important thing: The consumer we built so far only broadcasts messages. It doesn't save them in your database.

For a real chat app, you need to persist messages.

I recommend this architecture:

| Operation             | Technology                     |
| --------------------- | ------------------------------ |
| Register and login    | DRF + JWT                      |
| Create conversation   | DRF                            |
| Get conversation list | DRF                            |
| Load old messages     | DRF                            |
| Send a new message    | WebSocket                      |
| Receive new messages  | WebSocket                      |
| Save new message      | Django ORM inside the consumer |
| Mark message as read  | DRF or WebSocket               |

For example, when Flutter sends a message, your consumer should:

1. Get the authenticated user from `self.scope["user"]`.
2. Validate the message and conversation membership.
3. Save the message in your `Message` database model.
4. Broadcast the saved message to the conversation group.

Because we're using an asynchronous consumer, database operations should use `database_sync_to_async` or Django's supported asynchronous ORM methods.

For example, a database helper could look like:

```
from channels.db import database_sync_to_async@database_sync_to_asyncdef save_message(user, conversation_id, text):    return Message.objects.create(        sender=user,        conversation_id=conversation_id,        content=text,    )
```

This assumes your `Message` model has those fields; adapt them to your actual models.

Also, verify conversation membership before allowing a connection. For example, with a many-to-many field called `members`:

```
@database_sync_to_asyncdef is_conversation_member(user_id, conversation_id):    return Conversation.objects.filter(        id=conversation_id,        members__id=user_id,    ).exists()
```

Call this inside `connect()` before accepting the connection. Replace `Conversation` and `members` with your actual model and relationship names.

# **10. What happens when your JWT expires?**

Your WebSocket connection is authenticated when it is established.

Suppose your access token expires after 10 minutes.

Your Flutter application should:

1. Use the REST refresh endpoint to get a new access token.
2. Store the new access token securely.
3. Reconnect the WebSocket using the new token.

An existing WebSocket connection is not automatically reauthenticated just because the JWT expires. For long-lived connections, consider periodically checking token expiry or limiting connection lifetime.

Your existing Simple JWT refresh endpoint can handle the token renewal.&#x20;

# **11. Configure Redis and deploy to Railway**

For production, replace your local in-memory channel layer with Redis.

Install:

```
pip install channels_redis
```

In `settings.py`:

```
import osCHANNEL_LAYERS = {    "default": {        "BACKEND": "channels_redis.core.RedisChannelLayer",        "CONFIG": {            "hosts": [                os.environ["REDIS_URL"]            ],        },    },}
```

Add a Redis service to Railway and configure the `REDIS_URL` environment variable in your Django service.

The in-memory channel layer is suitable for local experiments, but it does not distribute messages between separate processes. Redis is the recommended production channel layer.&#x20;
